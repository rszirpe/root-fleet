How Auto-Wait, Bluetooth, and lights work

A gets first priority; others follow creation order. Heading-aware A* minimizes turns, then distance. Each step reserves its source and destination tiles until every dispatched command finishes. Adjacent starts and movement are allowed. Lower-priority robots wait on their tile with orange lights when traffic conflicts. A never yields; it routes around parked robots or flashes yellow if no route exists.

Virtual fleet registry -- unplaced robots stay on bench
        |
Placed robots: A, B, C, ...
        |
Shared map -> priority A* + space-time reservations
        |
        +-- clear route --> independent BLE queues --> completion barrier
        +-- B/C/... conflict -> motors halted + orange Auto-Wait
        +-- map blocked --> motors halted + flashing yellow

Any bumper -> halt fleet -> recover confirmed poses -> update shared map -> cascade replan
Any top touch -> halt fleet -> flashing red latch -> manual reset at marked starts

Auto-Wait resumes when traffic clears. It cannot resolve permanent occupied-space deadlocks by itself: if every route is held, the fleet remains stationary until you stop and change the layout. No robot is teleported or allowed to pass through a waiter.

Virtual cards have no fixed application limit; your map and Bluetooth adapter limit how many real robots can operate. Wheel encoders cannot detect every slip or external push. Physical fleet motion remains untested. Keep the page visible on a flat supported surface; a disconnected robot might not receive a stop request.

The documented LED packet controls the whole top cross: device 3, command 2, payload [animation, R, G, B]. It has no side selector. Hardware uses shared red blinking for turns. Completion flashes yellow, orange, then green.
